# 调节归零与架构前后画面差异排查

审查基线：`fbad406`，2026-09-07。用户反馈普通图片与 RAW 都存在归零后仍有调整、架构调整后效果变化明显的现象。本次完成代码追踪和数值复现，未修改产品行为。

结论：有两个会同时影响普通图片和 RAW 的预览问题；RAW 另有 HDR 范围与基础曝光耦合的问题。最近 `fbf53f7` 引入的 PhotoRenditions 架构也确实改变了 gain map 的空间处理，但不能把所有差异都归因于这次重构。

## 1. “原图”实际保存了首次带调整的底图

位置：`apps/panel/web/js/preview/stage.js:620`、`:517`、`:539`；`apps/panel/web/js/settings/schema.js:67`。

新照片进入 `preparePhoto()` 后使用默认设置，默认亮度为 **+0.6 EV**。`load()` 把当前设置提交给原生渲染器，然后将返回的 `preview.base` 保存为 `image.original`。因此，“原图”虽然不跟随后续滑块更新，却已经包含首次曝光和显影。开启记住调整时，首次帧还可能含有保留的设置。

数值复现：输入线性灰色 RGB=(0.18, 0.18, 0.18)，按面板默认亮度和扩展起点生成的底图为 **0.272514**。之后把亮度调回零，输出回到 0.18，比较侧却仍为 0.272514。这足以让用户觉得归零后图片仍被压暗。

这是比较基准错误。对应的“原图”直方图也来自这份首次底图，不能用它证明与文件原始像素一致。此逻辑在最近 PhotoRenditions 改动之前已经存在；`f22ef99` 已出现这项赋值，+0.6 EV 默认值可追溯至 `83306b8`。

## 2. SDR 预览在零增益时仍二次压缩高光

位置：`apps/panel/web/js/preview/cpu.js:8`、`:29`；`apps/panel/web/js/preview/sdr-gpu.js:24`；`apps/panel/web/js/preview/stage.js:306`。

CPU 和 WebGL 效果侧无条件使用高光函数：

```text
v <= 0.8: v
v > 0.8: 0.8 + 0.2 × (1 − exp(−(v − 0.8) / 0.2))
```

比较侧直接显示底图，不经过该函数。即使原生输出 HDR=SDR、增益为零，显示端仍会改动亮部。SDR JPEG 也走这条效果显示路径，所以已经完成 SDR 映射的像素会再次被压缩。逐 RGB 通道处理还会改变亮部的通道比例。

直接调用生产代码 `planeToImageData()` 的结果：

| 相同输入线性通道 | 比较侧 8-bit | 效果侧 8-bit | 效果侧线性值 |
| --- | ---: | ---: | ---: |
| 0.18 | 118 | 118 | 0.18 |
| 0.80 | 231 | 231 | 0.80 |
| 0.90 | 243 | 241 | 0.878694 |
| 1.00 | 255 | 247 | 0.926424 |

这项差异属于预览显示，并不意味着文件导出也套用了同一个函数。真正的 WebGPU HDR 路径没有该额外高光函数。CPU 中此行为在 `ebcb341` 时已经存在，不能称为最近重构新增。

## 3. RAW 的 HDR 范围会改变基础自动曝光

位置：`apps/panel/hyperdr_panel/command.py:154`；`modules/look/src/photographic.cpp:73`。

面板的亮度零实际表示 `exposure_bias=0`，仍发送 `exposure=auto`。自动曝光计算把用户的 HDR 范围作为 `highlight_limited_exposure()` 的峰值预算；将范围归零，就可能要求自动曝光大幅降低整幅图的亮度，以保护高光。HDR 强度为零时，这个计算依然存在。

合成场景复现：256×128，前 240 列 RGB=(0.06, 0.051, 0.042)，其余 16 列为 (8, 6.8, 5.6)，无拍摄元数据；零曝光补偿、零 HDR 强度、扩展起点 0.25。

| HDR 范围 | 自动曝光 |
| --- | ---: |
| 2.5 档 | +1.10658 EV |
| 0 档 | −1.70639 EV |

曝光决策相差 **−2.81297 EV**，底图也随之变化。这个数字属于该合成场景，不是所有 RAW 的固定偏移。

另外，RAW 默认仍有对比度 1.08、自然饱和度 0.12、暗部曲线、最低 0.08 的局部清晰度系数和高光趋白。它们不受 HDR 强度归零控制。RAW 必须经过白平衡、去马赛克和显示映射才能观看，但这些额外风格参数应与用户理解的“无调整基准”明确区分。

这项曝光耦合可在重构前的摄影渲染代码中找到。新架构的 SDR JPEG 路由另外固定了肩部并将 HDR 预算归零，因此 RAW 在切换 SDR/HDR 输出格式时也可能改变底图；相关处理见 `modules/look/src/render_options.cpp:5`，不是单纯更换编码器。

## 4. 新架构对 gain map 多做了一次空间平均

位置：`modules/look/src/rendition.cpp:148`、`:203`；`modules/gainmap/src/rendition.cpp:42`。

旧路径把局部增益网格量化后插值重建。当前手动路径先将局部增益网格插值为全尺寸 HDR 图，选择 Adaptive HDR / Ultra HDR 时，再从全尺寸 SDR/HDR 亮度比按网格平均、量化，最后再次插值重建。

因此，架构调整不是像素等价的搬迁。局部高反差边缘会受到额外空间平均，量化和插值的顺序也变了。直接 PQ/HLG 输出使用浮点 HDR 图，不经历这次反推 gain map，因而不同输出格式也不保证逐像素相同。

本次在同一个当前 Release 构建中，对照保留的旧入口 `make_gain_map()` 与生产使用的 `render_renditions()` → `gain_map_from_renditions()`，均不使用 LUT：

| 输入与参数 | 底图最大通道差 | HDR 最大通道差 |
| --- | ---: | ---: |
| SDR 渐变，亮度 0、强度 0 | 0 | 0 |
| SDR 渐变，亮度 0、强度 0.4 | 0 | 0.004003 |
| RAW 场景，亮度 0、强度 0 | 0 | 0 |
| RAW 场景，亮度 0、强度 0.4 | 0 | 0.153716 |
| RAW 场景，亮度 0、强度 1 | 0 | 0.850486 |

这里通道值是相对 SDR 白=1 的线性光值。RAW 场景使用上一节的明暗边界，范围 2.5 档、区域参与 1。强度 0.4 时最大差位于高光边界，旧值 1.77486、新值 1.62115，约下降 **8.7%**；强度 1 时同一边界约下降 **20.3%**。整图峰值变化很小，因此只检查峰值或 headroom 不能发现这类局部变化。

SDR 渐变为 256×128，R=0.01+0.99×x/255，G=0.85R，B=0.7R。零参数时它与源像素完全一致，证明此正常 SDR 输入并没有在新原生底图渲染阶段被无条件加上摄影曲线。

这个对照隔离了渲染路径差异，**不是安装旧版应用后对用户原照片的完整历史复现**：两条路径共享当前解码、色彩与局部分析实现。没有证据把此前 RAW 校准修复、设备显示差异或所有历史版本差异混为同一个原因。

## 5. “重置全部”目前也不表示归零

位置：`apps/panel/web/js/settings/controls.js:346`。

按钮恢复 schema 默认值，包括亮度 +0.6 EV、HDR 强度 0.4、范围 2.5 档；不会恢复为无效果。手动把可见滑块归零则仍有上述比较基准、SDR 显示和 RAW 基础显影的问题。两种操作需要分别定义，不能用“重置成功”作为像素无变化的证据。

## 建议修复顺序

1. 独立生成比较基准：普通 SDR 使用无 LUT、零曝光补偿的解码结果；RAW 使用固定且明确的基础显影。不要把当前首次效果帧标成原图。
2. SDR 显示应保证 HDR=SDR 时效果侧与底图相同。SDR JPEG 直接显示已生成的 SDR 图；如保留 HDR 效果模拟，应以底图为基准设计映射，使零增益严格回到基准。
3. 将 RAW 基础曝光与 HDR 扩展预算分开，避免 HDR 范围归零改变整幅底图。明确基础显影、默认增强和重置的产品语义。
4. 修正 gain map 输出的重复空间处理。无 LUT／保持公共 RGB 增益的情况应避免不必要的网格重建与再平均；验证明暗边界，而不只比较全图峰值。
