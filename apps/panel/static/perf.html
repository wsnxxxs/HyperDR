面板滑杆性能自测

对本次「交互层修复」的三处改动做改前 / 改后对照。改前的实现按原样复制到本页， 改后的路径直接调用 js/ 下的真实模块，两者跑同一组输入。
需要通过面板服务打开（http://…/perf.html），ES module 不能用 file:// 加载。 测量结果与机器和浏览器相关，关掉 DevTools 再跑数值更干净。

1. 曲线表重建（curve.js · refreshTable）

一次拖动里，只有 6 个参数会改变曲线形状。改动 HDR 扩展强度、按住看原图、切换直方图模式 都不属于这 6 个，但改前的代码仍然每帧走 257 次 Math.pow。 这里模拟一次拖动中「形状参数不变」的绝大多数帧。

2. 画布上下文（cpu.js · willReadFrequently）

显示画布只被写入，从不 getImageData。改前请求了 willReadFrequently， 浏览器因此把画面留在系统内存里用软件合成。这里对同尺寸的两块画布做同样次数的 putImageData 加一次合成绘制。

3. 滑杆回写（controls.js · apply）

拖动时 apply 会把值写回正在被手指按住的 input，并每帧重设 max 与 --fill。这里对一个真实 range 元素跑两种 apply， 每帧强制读一次布局，把样式重算的代价计进来。耗时之外，改前那条路径还会在拖动中 重新落位滑块——这一点是手感问题，数字量不出来，见下方第 5 节。

4. 完整设置流水线（真实 store + 真实 controls）

挂载真实的 mountControls，模拟连续拖动 HDR 扩展强度：每帧 store.set → 微任务 flush → 所有 watcher 的 apply → 强制布局。 测的是一次滑杆输入在预览渲染之前要付的固定成本。

5. 手感实测（需要你亲手拖）

用真实滑杆测「输入 → 上屏」延迟：记录每个 input 事件到下一帧渲染回调的间隔， 以及相邻两帧的间隔。桌面端目标是 p95 延迟 < 20ms、掉帧 0；触屏上重点看 touch-action 是否消掉了起手的那一下停顿——横向拖应当立刻跟手。
